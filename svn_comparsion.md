# Git vs SVN: ветвление, коммиты и сценарии использования

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

Git:
- Ветка — это всего лишь указатель на коммит (файл размером ~41 байт, содержащий SHA-1 хеш).
- История в Git — это DAG (направленный ациклический граф) коммитов, где каждый коммит ссылается на родителя. Создание ветки = создание новой ссылки на существующий коммит.
- Переключение между ветками (git checkout) — это смена указателя HEAD + обновление рабочей директории. Операция почти мгновенная.
- Слияние отслеживается через общих предков (merge base), а не через копирование файлов.

SVN:
- Ветка — это физическая копия директории внутри репозитория (по соглашению branches/, tags/, trunk/).
- Создание ветки = операция svn copy, которая на сервере создаёт новую структуру (пусть и с экономией места через механизм «cheap copies», но всё равно это отдельный узел в дереве ревизий).
- Переключение между ветками (svn switch) требует сетевого взаимодействия с сервером и синхронизации рабочей копии.
- История линейна (по ревизиям), а ветки — это просто разные пути в дереве. Отслеживание родства веток усложнено.

Итог: в Git ветка — это ссылка в графе; в SVN — это копия директории в централизованном репозитории.

## 2. Можно ли в SVN сделать коммит без интернета?

Нет, нельзя (в обычном режиме).

Причины:
- SVN — централизованная VCS. Репозиторий находится на сервере, а рабочая копия — лишь «снимок» файлов + скрытая директория .svn с метаданными.
- Коммит (svn commit) отправляет изменения напрямую на сервер, где создаётся новая ревизия. Без соединения с сервером ревизию создать негде.
- Локально можно делать только svn add, svn delete, svn revert — то есть менять рабочую копию, но не фиксировать историю.

Исключения / обходные пути:
- svn diff > patch — сохранить изменения в файл и применить позже.
- Локальный репозиторий через svnadmin create + file:// — но это уже не «без сервера», а «сервер на этой же машине».

В Git же коммит — локальная операция, поэтому работа без интернета — норма.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

| Сценарий | Почему SVN |
|---|---|
| Хранение больших бинарных файлов (арт, CAD, видео) | SVN умеет блокировки (svn lock), частичные checkout (--depth), не тянет всю историю. Git плохо работает с бинарями (LFS решает, но добавляет сложность). |
| Жёсткий контроль доступа по путям | В SVN права (read/write) настраиваются на поддиректории через authz. В Git разграничение по путям внутри репозитория — нетривиально. |
| Централизованное управление и аудит | Единый сервер = единая точка контроля, проще для регуляторов (банки, госструктуры). |
| Крупные монорепозитории с частичным checkout | SVN позволяет выкачать только нужную подпапку. Git требует клонировать весь репозиторий (sparse-checkout частично решает, но ограниченно). |
| Команды с низкой квалификацией в VCS | Линейная модель SVN проще для понимания: «есть trunk, есть branches». Git с его staging area, rebase, detached HEAD пугает новичков. |
| Legacy-интеграции | Многие старые CI/CD, IDE и корпоративные системы исторически заточены под SVN. |
| Юридические требования к «единому источнику правды» | Некоторые нормативы требуют централизованного хранения кода с версионированием — SVN ложится естественнее. |
| Огромные репозитории с долгой историей | Клонирование Git-репозитория на десятки ГБ может занимать часы; SVN позволяет работать с частью дерева. |

Когда Git однозначно лучше:
- распределённая команда,
- частая работа с ветками и code review,
- open-source,
- необходимость работать офлайн,
- сложные merge-сценарии.
